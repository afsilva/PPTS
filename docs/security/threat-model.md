# Threat model

**Owner:** Maintainers · **Last reviewed:** 2026-11-08 · **Method:** lightweight STRIDE + abuse cases

## Assets

Identity/session material, authorization assignments, employee PII, project/client data, time records, billing rates, project notes/documents, audit evidence, credentials, backups, and build artifacts.

## Actors

Employees, managers, administrators, auditors, unauthenticated attackers, compromised accounts, malicious insiders, and compromised dependencies/build systems.

## Primary abuse cases and controls

| Abuse case                             | Primary controls                                                                                                                                                                                                                                     |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Change another worker's status/time    | Session-derived actor; resource policies; no actor form field; negative tests; audit                                                                                                                                                                 |
| Create overlapping/open entries        | Serializable transactions; per-user row lock; PostgreSQL partial unique index; actor-scoped replay receipts; concurrency and retry tests                                                                                                             |
| Inject SQL/script/content              | Prisma parameter binding; Zod allowlists/limits; React encoding; no raw HTML; CSP                                                                                                                                                                    |
| Traverse/delete/upload arbitrary files | No filesystem-derived client paths; random private object keys; membership checks; quarantine/scanning; CSRF/origin checks                                                                                                                           |
| Steal or replay sessions               | Current local: validated OIDC, encrypted HttpOnly SameSite cookies, absolute/idle expiry, five-active-session cap, revocation/cleanup, provider logout. Production: HTTPS Secure cookies, MFA, edge rate controls, and approved key/session rotation |
| Abuse admin capability                 | Explicit policies, least privilege, reauthentication for sensitive changes, immutable audit, alerting                                                                                                                                                |
| Expose PII via logs/reports            | Data minimization, field policy, redaction, retention, authorized exports, no sensitive telemetry                                                                                                                                                    |
| Poison dependencies/builds             | Lockfile, automated updates, SCA/SAST/secrets, protected reviews, pinned actions/images, SBOM/signing roadmap                                                                                                                                        |
| Cause resource exhaustion              | Proxy body/time limits, rate limits, quotas, pagination, DB timeouts, bounded uploads                                                                                                                                                                |
| Hide actions by altering audit events  | Append-only service, separate DB privileges and centralized export in production                                                                                                                                                                     |
| Fail open during DB/IdP/storage faults | Typed errors, generic responses, transactions, timeouts, deny on policy uncertainty, fault tests                                                                                                                                                     |

## Current residual risks

Project documents now use generated opaque keys, normalized display names, exact-Origin one-file multipart parsing, hard byte/count quotas, strict extension/signature agreement, SHA-256 integrity, private quarantine and clean areas, and a separate ClamAV worker. Scanner failures and integrity uncertainty remain unavailable; only `AVAILABLE` objects receive freshly authorized, audited, application-proxied attachment downloads. Delete first makes the row inaccessible, then purges both areas and preserves an audit tombstone. Local Compose isolates ClamAV on an internal network with no host port. Production still requires independently credentialed encrypted object storage, scanner-signature freshness alerts, durable cross-replica leases, ingress-rate quotas, approved retention/legal holds, reconciliation, and restore testing.

The first business slice is database-backed. Acting identity comes only from the validated session; employees can change only their own clock/presence; project selection requires active catalog records and server-verified membership; and administrators or project-scoped managers can assign active members. Project, membership, document, and reporting services recheck the actor's active database state so stale actor objects and memberships do not restore disabled-account access. Manager reports query only database-verified `MANAGER` projects, and project updates verify the same scope; PostgreSQL and real OIDC/HTTP tests cover inactive and out-of-scope denials without side effects. Cookie-authenticated URL-encoded mutations require an exact Origin, a 16 KiB streaming body limit, and tighter field-level schemas; multipart document requests use their separate bounded parser and quota boundary. Time transitions serialize on the actor's user row, execute transactionally, and retain PostgreSQL constraints as final defenses. Clock and presence forms supply strict UUID submission keys, but never an actor ID. A receipt primary key combines the session-derived actor and submission ID; its SHA-256 fingerprint binds the action to normalized command fields while retaining no plaintext status message. Exact retries return the original resource, whereas action or payload mismatch fails closed. Receipt, state transition, and one success audit commit atomically; failed transitions leave no receipt. Receipts expire after 24 hours and are removed with inactive sessions by a least-privilege scheduled maintenance service that retries failures and emits only aggregate counts. Success audits commit atomically; failure audits contain only actor, operation, resource type, outcome, and a stable reason—never submitted status text, bodies, tokens, or credentials. Status-board fields are deliberately limited.

Account/profile linking accepts only bounded UUID/version input, requires an administrator session, locks both rows, permits only active unlinked accounts and non-archived employee profiles, relies on one-to-one and employee-kind database constraints, increments optimistic versions, and audits atomically. It does not mutate Keycloak passwords or roles. Monthly exports repeat report authorization and project scope, set private no-store headers, quote every CSV cell, and neutralize spreadsheet formula prefixes. The administrator audit UI bounds pagination and exposes allowlisted metadata only. Remaining production blockers include authorization capabilities outside the shipped time/project/report/document slice, business-owner approval and reconciliation of the production organization timezone, distributed edge rate limiting, monitoring scheduled session/receipt cleanup, durable audit export/alerting and retention, production HTTPS/MFA/managed-secret integration, signed release provenance/SBOM controls, broader abuse/fault tests, and full business-flow coverage. The dashboard's independent reads may briefly represent different committed moments during concurrent transitions, although stored state remains transactionally consistent. CSP temporarily permits inline style for chart rendering.

## Review triggers

Review this model for every authentication/authorization change, new external integration, PII field, upload format, public API, tenancy decision, deployment topology, or security incident—and at least every six months.
